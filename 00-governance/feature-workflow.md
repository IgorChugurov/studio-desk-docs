# Сквозной процесс фичи

**Scope:** как одна фича проходит путь от обсуждения до принятого результата.

## Эссе — что это

Процесс описывает этапы работы над фичей и условия перехода между ними. Проект ведётся от документации: сначала утверждается канон темы, затем на его основе даются задания дизайнеру, бэкенду и фронтенду. Каждый этап имеет результат и условие, при котором можно идти дальше. Решает владелец проекта.

## Эссе — как это работает

1. **Приём задачи.** Агент пересказывает задачу в 2–3 предложениях и останавливается. Работа начинается после подтверждения или поправки.
2. **Обсуждение темы** в чате: цель, границы, что не входит, открытые вопросы. Файлов нет. Переход: владелец сказал «тема согласована».
3. **Канон темы** в `01-product/`. В нём есть раздел «Потоки по шагам» по стандарту `02-design/flow-design.md`: шаги, состояния, ошибки, фиксированные тексты. Переход: явное «ОК» на запись.
4. **Задание дизайнеру** в папке темы в `01-product/`: что и зачем, сценарии, какие данные и действия, состояния; потоки по шагам берутся из канона по стандарту `02-design/flow-design.md`. Раскладку и компоненты выбирает дизайнер. Результат — Figma (если в текущем срезе Figma не делается, источником раскладки, состояний и фиксированных текстов служит раздел «Потоки по шагам» канона темы и дизайн-кит проекта). Переход: владелец принял Figma (или потоки в каноне). Если при рисовании макетов нашлись новые состояния, инварианты или изменения потока, сначала синхронизируем канон темы.
5. **Задание бэкенду:** что обязательно, что бэкенд решает сам, критерии приёмки. Результат задания — согласованный контракт API. Затем реализация по срезам/фазам: план по файлам (6 пунктов контракта плана) → «ОК» → правка → проверка по Test plan → реальный diff → приёмка. Если при реализации бэкенда обнаружились новые инварианты или уточнения API (`*-backend-brief-feedback.md`), они синхронизируются с каноном темы (`01-product/<тема>/`) и `api-contract.md` до старта (или перед очередным срезом) фронтенда.
   Этапы 4 и 5 идут после канона и могут выполняться параллельно.
6. **Задание фронтенду:** потоки по шагам из канона (и узлы Figma, когда она есть), кит и типы страниц (`02-design/ui-kit-and-pages.md`), контракт API. Начинается, когда приняты потоки/Figma (этап 4), согласован контракт API (этап 5) и в канон темы внесены уточнения после дизайна и бэкенда. Сначала разметка экрана (`Screen mapping` по `02-design/ui-kit-and-pages.md`) и план среза (6 пунктов, включая Specify и Test plan) → «ОК», затем реализация, проверка по Test plan (и сверка с Figma по свойствам, когда есть макет), приёмка.
7. **Завершение.** Документы обновлены, если поведение изменилось. Коммит делается только по явной просьбе владельца.

## Эссе — лёгкий маршрут для мелких правок

Для небольшой правки без новой логики полный процесс не нужен. Маршрут: короткий план в чате → «ОК» → правка → реальный diff → приёмка → коммит по просьбе. Если правка меняет описанное в каноне поведение или выходит за границы мелкой, она переходит на полный процесс.

## Эссе — как связано

Связано с правилами документации (`documentation-rules.md`), шаблонами заданий (`templates/`), правилами согласования (`approval-rules.md`) и записями задач (`work-items.md`).

## Агент — правила

| Правило | Детали |
|---|---|
| Этапы | Не пропускаются |
| Пробел или новый инвариант в каноне | На любом этапе (включая возврат после Figma или `*-backend-brief-feedback.md`): остановиться, сначала синхронизировать канон темы и `api-contract.md`. Канон главнее заданий. Критерии приёмки (`Specify`) и план проверки (`Test plan`) развиваются рука об руку с каноном и кристаллизуются перед реализацией каждого среза |
| План реализации | Показывать на «ОК» для изменений кода/продукта только с шестью пунктами: (1) **причина** (`Cause`), (2) **переиспользование** (`Reuse` — что уже есть в проекте), (3) **обратная совместимость** (`Compatibility` — все места использования изменяемого кода), (4) **зона влияния** (`Blast radius`), (5) **критерии приёмки среза (`Specify`)** — короткий список наблюдаемых результатов (`AC-1..AC-N`), по которым принимается срез (без отдельного PRD), (6) **план проверки (`Test plan`, 1:1 к `Specify`)** — на каждый критерий одна проверка: чем смотрим (`pnpm test`, запрос API, ручной шаг по потоку) и что считается несданным (для экранов/потоков — привязка к шагу потока в каноне темы и узлу Figma, когда он есть). Декомпозиция остаётся линейной очередью срезов/фаз без отдельного графа зависимостей |
| Область «ОК» | Разрешает только названное. Смежные правки, новые файлы, коммит — отдельно |
| Несколько результатов | По одному, каждый со своей приёмкой |
| Провал приёмки | Если результат противоречит заявлению «готово»: остановиться, назвать факт, одна гипотеза, один план, ждать |
| Коммит | Только по явной просьбе, после приёмки |
| Структура данных | Структуру данных обсуждаем и согласовываем до любой реализации, которая её хранит. В обсуждении: сущности, поля, связи, что уникально, что удаляется, а что остаётся. Таблицы не создаются, пока владелец не сказал «ОК» на структуру. Один факт хранится в одном месте, связь идёт по идентификатору, а не копией текста, поле «на всякий случай» не добавляется |

## Агент — лёгкий маршрут

- Шесть пунктов плана реализации (включая 1-строчный `Specify` и `Test plan`) сохраняются, но коротко (по одной строке).
- Не применяется, если правка затрагивает канон, контракт API, общий код или более одного репозитория.
