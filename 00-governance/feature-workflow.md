# Сквозной процесс фичи

**Scope:** как одна фича проходит путь от обсуждения до принятого результата.

## Эссе — что это

Процесс описывает этапы работы над фичей и условия перехода между ними. Проект ведётся от документации: сначала утверждается канон темы, затем на его основе даются задания дизайнеру, бэкенду и фронтенду. Каждый этап имеет результат и условие, при котором можно идти дальше. Решает владелец проекта.

## Эссе — как это работает

1. **Приём задачи.** Агент пересказывает задачу в 2–3 предложениях и останавливается. Работа начинается после подтверждения или поправки.
2. **Обсуждение темы** в чате: цель, границы, что не входит, открытые вопросы. Файлов нет. Переход: владелец сказал «тема согласована».
3. **Канон темы** в `01-product/`. В нём есть раздел «Потоки по шагам» по стандарту `02-design/flow-design.md`: шаги, состояния, ошибки, фиксированные тексты. Переход: явное «ОК» на запись.
4. **Задание дизайнеру** в папке темы в `01-product/`: что и зачем, сценарии, какие данные и действия, состояния; потоки по шагам берутся из канона по стандарту `02-design/flow-design.md`. Раскладку и компоненты выбирает дизайнер. Результат — Figma. Переход: владелец принял Figma. Если дизайнер нашёл пробел, возвращаемся к канону.
5. **Задание бэкенду:** что обязательно, что бэкенд решает сам, критерии приёмки. Результат задания — согласованный контракт API. Затем реализация: план по файлам → «ОК» → правка → реальный diff → приёмка.
   Этапы 4 и 5 идут после канона и могут выполняться параллельно.
6. **Задание фронтенду:** Figma, кит, тип страницы, контракт API. Начинается, когда приняты Figma (этап 4) и согласован контракт API (этап 5); готовая реализация бэкенда для старта не требуется. Сначала разметка экрана → «ОК», затем реализация, сверка с Figma по свойствам, приёмка.
7. **Завершение.** Документы обновлены, если поведение изменилось. Коммит делается только по явной просьбе владельца.

## Эссе — лёгкий маршрут для мелких правок

Для небольшой правки без новой логики полный процесс не нужен. Маршрут: короткий план в чате → «ОК» → правка → реальный diff → приёмка → коммит по просьбе. Если правка меняет описанное в каноне поведение или выходит за границы мелкой, она переходит на полный процесс.

## Эссе — как связано

Связано с правилами документации, шаблонами заданий и правилами согласования (в `00-governance/`, будут описаны отдельно).

## Агент — правила

| Правило | Детали |
|---|---|
| Этапы | Не пропускаются |
| Пробел в каноне | На любом этапе: остановиться, сначала исправить канон. Канон главнее заданий |
| План реализации | Показывать на «ОК» только с четырьмя ответами: причина, что уже есть и можно переиспользовать, обратная совместимость, зона влияния |
| Область «ОК» | Разрешает только названное. Смежные правки, новые файлы, коммит — отдельно |
| Несколько результатов | По одному, каждый со своей приёмкой |
| Провал приёмки | Если результат противоречит заявлению «готово»: остановиться, назвать факт, одна гипотеза, один план, ждать |
| Коммит | Только по явной просьбе, после приёмки |

## Агент — лёгкий маршрут

- Четыре ответа плана сохраняются, но коротко.
- Не применяется, если правка затрагивает канон, контракт API, общий код или более одного репозитория.

## Открытые вопросы

- Точные границы мелкой правки.
