# Устройство бэкенда

**Scope:** как устроено Nest-приложение StudioDesk: три API, разделение кода, два слоя защиты данных, пользователи PostgreSQL, локальное окружение и сервер.

## Эссе — что это

Бэкенд StudioDesk — одно Nest-приложение (модульный монолит) с одной базой PostgreSQL. Через него работают три поверхности продукта: админка платформы, админка студии и публичный сайт студии. У каждой поверхности своё API, своя авторизация и свой уровень доступа к данным.

## Эссе — три API

| API | Путь | Кто пользуется |
|---|---|---|
| Админка платформы | `/api/platform/...` | администратор платформы |
| Админка студии | `/api/studio/...` | владелец и сотрудники студии |
| Публичный | `/api/public/...` | сайт студии и клиенты |

Принадлежность кода к API определяется папкой: `src/apis/platform`, `src/apis/studio`, `src/apis/public`. В папке API лежат его контроллеры и guards. Общая бизнес-логика живёт в отдельных модулях и используется разными API.

У каждого API свой guard авторизации, который подключается ко всем контроллерам этого API сразу, а не ставится вручную на каждый метод. Всё, что лежит в папке API, проходит его проверку. Открытые адреса явно помечаются декоратором.

## Эссе — два слоя защиты данных

1. **Приложение — основной слой.** Guards и сервисы решают, кто пользователь, действует ли токен и что ему разрешено. Это может проверить только приложение.
2. **База — второй слой.** У каждого API свой пользователь PostgreSQL с правами только на нужные таблицы и действия. Даже при ошибке в коде база отклонит то, что этому API не разрешено. Например, если права на удаление студий не выдано никому, студию не удалить никаким кодом.

Права в базе выдаются на таблицы целиком. Ограничение по строкам одной студии (RLS по `studio_id`) добавляется с первой фичей, где появляются данные студии. Чтобы добавить RLS без переделки схемы, каждая таблица данных студии с самого начала содержит колонку `studio_id`.

## Эссе — пользователи PostgreSQL

Пользователь PostgreSQL — это логин и пароль, под которым программа подключается к базе. Люди (администратор платформы, владельцы, клиенты) пользователями PostgreSQL не являются, они — строки в таблицах.

| Пользователь | Кто подключается | Что может |
|---|---|---|
| `studio_desk_owner` | только миграции | владеет таблицами, создаёт и меняет их |
| `platform_api` | код API админки платформы | только выданные ему права |
| `studio_api` | код API админки студии | только выданные ему права |
| `public_api` | код публичного API | только выданные ему права |

Пользователи API не могут создавать, менять или удалять таблицы. У каждого API своё подключение к базе под своим пользователем.

Пользователей создаёт стартовый скрипт, а не миграция:
- миграции лежат в открытом репозитории и одинаковы для всех окружений, а пароли разные в каждом окружении и в репозиторий не попадают;
- создавать пользователей может только главный администратор базы, а миграции выполняет `studio_desk_owner`.

Локально скрипт выполняет Docker при первом запуске пустой базы, пароли берутся из локального `.env`. На сервере выполняется тот же скрипт с паролями из серверного `.env`.

## Эссе — права на таблицы

Каждая миграция, которая создаёт таблицу, в том же цикле явно выдаёт права пользователям API. Пока права не выданы, у API нет доступа к таблице.

В репозитории бэкенда лежит файл ожидаемых прав: для каждой таблицы — какие права у каждого пользователя API. Тест сравнивает реальные права в базе с этим файлом. Лишнее право или забытая таблица роняет тест. Изменить права можно только явно, через этот файл, и такая правка видна на ревью.

## Эссе — окружение и сервер

- **Локально.** В Docker (Docker Desktop) работает только PostgreSQL, описанный в `docker-compose.yml` в репозитории бэкенда: конкретная основная версия (не `latest`), стартовый скрипт, постоянное хранилище данных. Nest запускается прямо на Mac.
- **Сервер.** Бэкенд собирается по `Dockerfile`. Миграции выполняются отдельным шагом до запуска приложения под `studio_desk_owner`. Приложение работает под пользователями API и выполнять миграции не может.

## Агент — запреты

- Контроллер вне папки своего API.
- Код одного API использует подключение к базе другого API.
- Таблица без явно выданных прав или без записи в файле ожидаемых прав.
- Право, не нужное API для его задач.
- Миграции под пользователем API; приложение под `studio_desk_owner`.
- Создание пользователей PostgreSQL или пароли в миграциях.
- Секреты в репозитории.
- Таблица данных студии без колонки `studio_id`.

## Агент — чеклист новой таблицы

- [ ] Таблица создана миграцией
- [ ] В миграции выданы права каждому пользователю API, которому таблица нужна, и только нужные
- [ ] Файл ожидаемых прав обновлён
- [ ] Тест прав проходит
- [ ] Если таблица хранит данные студии, в ней есть `studio_id`
