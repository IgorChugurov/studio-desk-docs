# Общие правила API

**Scope:** правила, общие для всех трёх API StudioDesk и для фронтенда, который с ними работает: проверка входящих данных, формат ошибок, формат ответов, OpenAPI, адрес проверки работоспособности.

## Эссе — что это

Три API (см. `backend-structure.md`) устроены по одним правилам, чтобы фронтенд одинаково работал с любым из них. Этот документ — единственный источник правды по этим правилам и для бэкенда, и для фронтенда.

## Эссе — проверка входящих данных

Входящие данные каждого запроса (тело, параметры пути, query) описываются схемой Zod. Проверку выполняет один общий механизм, подключённый ко всем трём API. Неподходящие данные отклоняются до того, как дойдут до кода, с ошибкой, в которой названо поле. Поля, которых нет в схеме, отбрасываются: клиент не может подставить лишнее.

## Эссе — формат ошибок

Фронтенд показывает свои фиксированные тексты из дизайна, поэтому клиенту нужен машинный код ошибки, а не текст. Любая ошибка любого API имеет одну форму:

```json
{
  "statusCode": 409,
  "code": "SUBDOMAIN_TAKEN",
  "message": "Subdomain is already taken",
  "field": "subdomain"
}
```

- `statusCode` — HTTP-статус.
- `code` — машинный код. По нему фронтенд выбирает текст на экране.
- `message` — пояснение для разработчика. На экран не выводится.
- `field` — поле, к которому относится ошибка, если она относится к полю.

Ошибки проверки данных возвращаются с кодом `VALIDATION_ERROR` и списком `errors`, по одной записи на каждую ошибку поля:

```json
{
  "statusCode": 400,
  "code": "VALIDATION_ERROR",
  "message": "Validation failed",
  "errors": [
    { "code": "INVALID_FORMAT", "field": "email", "message": "Invalid email address" }
  ]
}
```

Коды ошибок поля: `REQUIRED`, `INVALID_TYPE`, `INVALID_FORMAT`, `INVALID_VALUE`, `TOO_SMALL`, `TOO_BIG`, `INVALID`. Для вложенных полей `field` — путь через точку, например `owner.email`.

Общие коды: `VALIDATION_ERROR`, `BAD_REQUEST` (неразборчивый запрос, например испорченный JSON), `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `INTERNAL_ERROR`. Коды конкретных фич (например, `SUBDOMAIN_TAKEN`) определяются в заданиях этих фич.

Внутренние подробности (текст ошибки базы, стек вызовов) клиенту не отдаются никогда, только в лог сервера.

## Эссе — успешные ответы

Ответ — сами данные, без обёртки. Формат списков и пагинации определяется в заданиях фич.

## Эссе — OpenAPI

У каждого API свой документ OpenAPI, который строится автоматически из кода и схем Zod. Документ доступен страницей в браузере и JSON-файлом. Из JSON фронтенд генерирует типы.

Страница — `/api/<platform|studio|public>/docs`, JSON — `/api/<platform|studio|public>/docs/json`.

Документация доступна только локально и в тестовом окружении. На сервере выключена.

## Эссе — проверка работоспособности

Адрес `/api/health` открыт без токена и отвечает, работает ли приложение и доступна ли база. Нужен серверу и Docker, чтобы понимать, живо ли приложение.

Ответ: `200 { "status": "ok", "database": "ok" }`; если база недоступна — `503 { "status": "error", "database": "unavailable" }`.

## Эссе — как связано

- Правила разработки бэкенда: `04-engineering-rules/backend.md`.
- Коды ошибок конкретных фич: задания бэкенду в `01-product/<тема>/`.

## Агент — контракт ошибки

- Каждая ошибка возвращается в форме выше, во всех трёх API.
- `code` обязателен и стабилен: переименование кода — изменение контракта.
- В ответе нет текста ошибок базы, стека вызовов и других внутренних подробностей.

## Агент — фронтенд

- Текст на экране выбирается по `code`.
- `message` не выводится пользователю.
- Ошибка поля показывается у поля из `field`.
- Типы запросов и ответов берутся из документа OpenAPI своего API, а не пишутся вручную.

## Агент — чеклист нового эндпоинта

- [ ] Лежит в папке своего API
- [ ] Входящие данные описаны схемой Zod
- [ ] Ошибки возвращаются в общем формате, коды фичи описаны в задании
- [ ] Эндпоинт виден в документе OpenAPI своего API
- [ ] Если эндпоинт открыт без токена, это помечено явно и оправдано заданием
