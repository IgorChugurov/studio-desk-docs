# Odoo или свой учётный слой: разбор для Studio Desk

Дата: 2026-11-18 · Автор: главный бот · Статус: рабочая заметка, **не канон и не решение**.
Повод: вопрос Игоря «поставить Odoo на свой сервер и работать через API, или переписать её на Nest, или делать свой учёт», с условием «бухгалтерия должна работать для многих разных организаций».

Обозначения: **[факт]** проверено по коду или документации (ссылка рядом); **[оценка]** моя оценка, не измерение; **[мнение]** моя позиция; **[не проверено]** надо уточнить.

## 0. Коротко

- Odoo 20.0 вышла в сентябре 2026; стандартная поддержка до сентября 2029 [факт, 1].
- Полноценная бухгалтерия (банковская сверка, финансовые отчёты, deferred revenue, бюджеты, консолидация) у Odoo — в **Enterprise**. В Community есть «Invoicing»: двойная запись, журналы, сторно, lock dates, мультивалютность, аналитика; недостающее частично закрывают модули OCA под **AGPL-3** [факт, 2–5].
- Модули Subscriptions, Appointments, Payroll — **только Enterprise**; POS и Loyalty — в Community [факт, код 20.0 + 2].
- Enterprise нельзя перепродавать, сублицензировать и распространять; лицензия привязана к подписке клиента на число пользователей [факт, 6, 7]. Значит, Enterprise внутри нашего SaaS для сотен организаций юридически и экономически не подходит.
- Community (LGPLv3) можно хостить и встраивать в SaaS; трудности не лицензионные, а архитектурные: изоляция тенантов, ресурсы, обновления, двойной UI и двойная модель данных.
- Переписывать Odoo на Nest **[мнение]** нереалистично: модуль `account` — около 45 тыс. строк Python без тестов и около 61 тыс. строк тестов, плюс он сильно опирается на ORM Odoo [факт, замер по клону].
- **Рекомендация [мнение]:** путь C — свой тонкий учётный слой в нашем Postgres (журнал событий + проводки по модели Odoo `account.move`/`account.move.line`, lock dates, сторно, последовательности), плюс выгрузка во внешнюю фискальную бухгалтерию (SK: SuperFaktúra / Pohoda; UA: BAS / M.E.Doc и ПРРО через Checkbox/Вчасно). Odoo — как источник паттернов и, возможно, как **один из коннекторов выгрузки** для клиентов, которые уже на Odoo.

## 1. Что умеет Odoo (на ноябрь 2026)

### 1.1 Версии и поддержка
- Текущая major-версия **20.0** (сентябрь 2026), в репо `odoo/odoo` есть ветки `19.0`, `20.0`, `saas-19.1…19.4`, `master` [факт, 1; `git ls-remote`].
- Major-версия выходит раз в год, стандартная поддержка 3 года, обновлять базу можно только на поддерживаемую версию [факт, 1]. Для нас это значит: **раз в 1–3 года миграция всех баз**.

### 1.2 Учёт: Community vs Enterprise

| Возможность | Community (LGPL) | Enterprise (OEEL) | Источник |
|---|---|---|---|

| Журналы, план счетов, налоги, фискальные позиции | да | да | код `account` |
| Состояния проводки `draft / posted / cancel`, типы (`entry`, `out_invoice`, `out_refund`, `in_invoice`…) | да | да | `account_move.py:138–159` |
| Сторно (`_reverse_moves`, кредит-ноты) | да | да | `account_move.py` |

Важная деталь про OCA [факт]: модули OCA — под **AGPL-3** (account-financial-tools, account-financial-reporting, account-reconcile, contract). Для ветки 20.0 на сегодня портирована малая часть: в `account-reconcile` 20.0 модулей ещё нет, в `account-financial-reporting` 20.0 только `account_tax_balance` [факт, GitHub API]. То есть Community + OCA реально живёт **на версию позади** Enterprise.

### 1.3 Локализации SK и UA
- `l10n_sk` (LGPL, автор 26HOUSE): словацкий план счетов 2020, базовые ставки DPH, фискальные позиции, налоговый отчёт (`tax_report.xml`), шаблон счёта [факт, `addons/l10n_sk/__manifest__.py`]. Это **план счетов + НДС**, а не полная словацкая отчётность. eKasa (фискализация наличных в SK) в модуле нет [факт: в модуле нет; что нужно по закону — **не проверено** в этом разборе].
- `l10n_ua` (LGPL, ERP Ukraine): план счетов П(С)БО, ~50 налогов, теги счетов; ~120 строк Python+XML, ~440 строк CSV [факт]. Ни отчётности, ни ПРРО, ни электронных документов.
- Odoo в документации перечисляет Slovakia и Ukraine среди фискальных локализаций [9], но по коду обе — минимальные.

### 1.4 Чем Odoo сильна [мнение на основе фактов выше]
- Зрелая, проверенная годами модель двойной записи: проводка = шапка `account.move` + строки `account.move.line`, балансировка (`check_move_validity`), сторно, сверка, курсовые разницы, налоги.
- Защита периода и неизменяемость продуманы на уровне данных (несколько lock dates, hard lock, исключения с аудитом, хеш-цепочка).
- Огромная экосистема (OCA, локализации, интеграции), готовый UI.

## 2. Мультитенантность: главный вопрос для нас

### 2.1 Вариант «multi-company в одной базе»
- Odoo multi-company задумана для **группы связанных компаний одного владельца**: общий план настроек, межкомпанийные сделки, сводные отчёты, переключатель компаний у пользователя [факт, 10].
- Контакты и товары по умолчанию **общие** для всех компаний; изоляция — через поле `company_id` и record rules [факт, 10].
- **Вывод [мнение]:** это не граница безопасности между чужими клиентами. Любой `sudo()` в кастомном модуле, ошибка в record rule или администратор базы видит всех. Для сотен независимых организаций — неприемлемо. Наш двойной фильтр (организация + роль) и отдельные DB-пользователи на API строже.

### 2.2 Вариант «база на организацию» (dbfilter)
- Odoo официально мультитенантна именно так: один сервер обслуживает много баз, база выбирается по хосту через `--db-filter` (`%h`, `%d`), рекомендуется `--no-database-list` и закрыть менеджер баз [факт, 11].
- В каждом worker-процессе на каждую базу загружается свой `Registry` (модели, кеши), они живут в LRU [факт, `odoo/orm/registry.py:96`]. **[оценка]** Сотни/тысячи баз = постоянная перезагрузка реестров, рост памяти, холодные запросы; cron обходит все базы.
- Создание базы = установка модулей `account` + локализация в каждую базу; обновление версии или своего модуля = `-u` по **каждой** базе. **[оценка]** На тысяче баз это отдельная операционная дисциплина (очереди миграций, откаты, мониторинг), которой у нас нет.
- Хостеры Odoo (сама Odoo Online, партнёры) живут как раз на database-per-customer [не проверено детально: по общедоступным сведениям], но у них целые команды эксплуатации.
- Пользователи и доступ: на каждую базу свои `res.users`; API-ключи привязаны к пользователю, у ключа обязательный срок, **максимум три месяца**, ключи надо ротировать [факт, 12]. Для тысячи баз это тысяча интеграционных пользователей и регулярная ротация ключей.

### 2.3 Итог по мультитенантности [мнение]
Odoo «рядом» для одного клиента — нормально. Odoo как общий учётный бэкенд для сотен малых организаций в нашем SaaS — это фактически запуск своего Odoo-хостинга: много баз, миграции раз в год, мониторинг Python-стека. Для одного разработчика с агентами — самый тяжёлый вариант по эксплуатации.

## 3. API

- **JSON-2** (`/json/2/<model>/<method>`), новый в 19.0: Bearer API-ключ, `X-Odoo-Database` при нескольких базах на домене, все аргументы именованные [факт, 12].
- XML-RPC `/xmlrpc`, `/xmlrpc/2` и JSON-RPC `/jsonrpc` **устарели в 19.0 и запланированы к удалению в Odoo 22** [факт, `addons/rpc/controllers/__init__.py`, ветка master].
- API — это не «бизнес-API», а удалённый вызов методов ORM (`search_read`, `create`, `action_post`…). Контракт = внутренние модели Odoo, они меняются между версиями (например, банковские выписки ушли из ядра в 16.0 [4]). **[мнение]** Стабильность контракта между версиями — наша забота.
- Транзакция: каждый вызов JSON-2 — отдельная транзакция [факт, раздел «Transaction» в 12]. Значит, «визит в нашей БД + проводка в Odoo» атомарно не сделать — нужен outbox и идемпотентность на нашей стороне в любом случае.
- Вебхуки: в Community есть исходящие (`ir.actions.server` тип `webhook`) и входящие (`base_automation`, триггер `on_webhook`) [факт, код].
- Важно: на **Odoo Online/облаке** внешний API доступен только на тарифе Custom [факт, 12]. Для self-hosted Community ограничения нет.

## 4. Интерфейс

- UI Odoo — отдельное приложение (OWL), со своей навигацией, логином, ролями и языками. Встроить его «внутрь» нашего Next.js кусками нельзя; можно только открыть Odoo как второй продукт.
- Бренд: Community под LGPL можно перекрашивать, но «Odoo» — зарегистрированный товарный знак Odoo S.A. [факт, 13]; называть сервис Odoo/«на Odoo» в маркетинге — риск, нужно своё имя [не юр. заключение].
- SSO: в Community есть `auth_oauth` (вход через OAuth2-провайдера), `auth_ldap`, `auth_totp`, `auth_passkey` [факт, код]. Наш вход можно сделать провайдером OAuth для Odoo, но это ещё один контур (маппинг наших ролей owner/administrator/accountant/specialist на группы Odoo, по каждой базе).
- UX [мнение]: Odoo Accounting рассчитана на бухгалтера. Владельцу фитнес-студии или салона нужен простой экран «деньги, абонементы, выплаты тренерам», а не план счетов. Наш модуль учёта всё равно придётся рисовать в нашем UI.

## 6. Объём и сложность (для пути B)

Замер по `odoo/odoo` master (20.0), 2026-11-18 [факт]:
- `addons/account`: ~45 тыс. строк Python без тестов (из них модели ~38.5 тыс., визарды ~4.5 тыс.), ~61 тыс. строк тестов, ~12 тыс. строк JS, ~13 тыс. строк XML; ~1270 объявлений полей; 57 файлов моделей.
- Ключевые файлы: `account_move.py` 8430 строк, `account_move_line.py` 4166, `account_tax.py` 5274, `account_payment.py` 1330.
- `account` зависит от `base_setup`, `product`, `analytic`, `portal`, `digest`, а `account.move` наследует `mail.thread`, `portal.mixin`, `sequence.mixin` и др. [факт, `__manifest__.py`, `account_move.py:83`].
- Ядро ORM (`odoo/orm`) — ~21.7 тыс. строк: вычисляемые и зависимые поля, onchange, record rules, multi-company, кеш, prefetch. Код `account` написан в терминах этого ORM; на Drizzle это не переносится механически.
- **[оценка]** Порт рабочего подмножества (проводки, налоги, сверка, сторно, lock dates, мультивалютность, отчёты) на Nest с сопоставимым поведением — **18–36 человеко-месяцев**, затем вечная самостоятельная поддержка форка без апстрима. С агентами быстрее писать, но не быстрее проверять корректность бухгалтерии.

## 8. Связь с OblikFlow

По репо `IgorChugurov/oblikflow-backend` и `oblikflow-fronend` [факт, просмотр дерева файлов]:
- Код: NestJS API на Supabase с модулями auth, enterprises, members, countries, currencies, locales, плюс SQL-миграции с RLS. **Проводок, регистров и периодов в коде нет.**
- Документы (фронтенд-репо, `docs/`): `LEDGER_STRUCTURE.md` (append-only регистры, GL-проводки debit/credit, `reversalOfId`, `periodId`, `configVersionId`, контекст REAL/SANDBOX), `PERIOD_MANAGEMENT.md` (статусы `open / closing / closed`, снимок при закрытии), `MULTI_TENANCY.md` (изоляция по `enterpriseId` + RLS), `MODULES_OVERVIEW.md` (документы, банк со сверкой, склад, налоги, зарплата, ОС).
- **[мнение]** Замысел OblikFlow уже по сути совпадает с путём C и с моделью Odoo. Значит, учётный слой Studio Desk стоит проектировать **как будущий клиент OblikFlow**: та же схема проводки, те же статусы периодов, чтобы потом перенести движок, а не переписывать.

| Нагрузка на одного разработчика | Высокая: второй стек (Python/OWL), хостинг, бэкапы, миграции, ключи | Очень высокая: огромный форк без апстрима | Низкая–средняя | Средняя (один коннектор) |
| Лицензии | Community — ок; Enterprise — нет; OCA AGPL при правках; товарный знак | LGPL-риск производного произведения | Чисто (идеи, не код) | Чисто |
| Сроки до первой ценности [оценка] | 1–2 мес. до пилота на одной базе; масштаб — долго | 18–36 чел.-мес. | 1–2 мес. на ядро журнала и отчёты | +2–4 нед. на коннектор |

| Связь с OblikFlow | Конкурирует с OblikFlow | Конкурирует / дублирует | Прямая ступень к OblikFlow | Прямая ступень |

**Вердикты [мнение]:**
- **A** — не как основной движок. Имеет смысл только как опциональная выгрузка для клиента, у которого уже есть своя Odoo.
- **B** — нет: объём, LGPL-риск, отказ от апстрима, и всё равно нет нашей доменной модели.
- **C** — да, как основной путь. Управленческий учёт свой и простой; фискальный учёт — у бухгалтера клиента во внешней системе через выгрузку/API.
- **Гибрид** — коннекторы (SuperFaktúra, Pohoda XML, Checkbox, Odoo JSON-2) добавлять по спросу рынка, а не заранее.

## 10. Что взять из Odoo в наш канон (идеи, не код)

| Паттерн Odoo | Закрывает наш пробел |
|---|---|
| Двухуровневая проводка: шапка `account.move` (дата, журнал, источник, состояние) + строки `account.move.line` (счёт, debit/credit или balance, валюта, сумма в валюте, партнёр, аналитика); сумма строк = 0 (`check_move_validity`) | **Схема события**: `accounting_events` = шапка факта, проводки = строки; инвариант баланса проверяется в БД |
| Состояния `draft → posted → cancel`; posted не редактируется | **Неизменяемость**: менять можно только черновик; после проведения — только сторно |
| Сторно через новую проводку со ссылкой `reversed_entry_id` (у Odoo `_reverse_moves`) | **Сторно**: вместо знака ±1 на событии — отдельная проводка-зеркало с `reversal_of_id`; знак ±1 можно оставить как удобное поле отчётов |
| Lock dates (общая, налоговая, продажи/закупки, hard lock) + исключения с аудитом (`account.lock_exception`) | **Закрытие периода**: `periods` со статусом `open / closing / closed` (как в OblikFlow) + «жёсткая» дата блокировки на организацию; исключения только с записью кто/когда/зачем |
| `sequence.mixin`: номера документов по журналу и году без дыр | Нумерация чеков/документов для экспорта во внешнюю бухгалтерию |
| Хеш-цепочка `inalterable_hash` | Доказуемая неизменяемость журнала (опционально, позже) |
| `Monetary` + валюта на строке, округление по `currency.rounding`, `account.cash.rounding` | **Деньги/округление**: хранить в minor units (целые центы/копейки) или `numeric(14,2)` + валюта на каждой строке; явное правило распределения остатка (100 € / 3 визита → 33.33 + 33.33 + 33.34) |
| `amount_currency` + валюта компании + курсы `res.currency.rate`, курсовые разницы | **Мультивалютность**: сумма в валюте операции и в валюте организации, курс на дату; запрет смены валюты организации после первой проводки |
| Партиальная/полная сверка (`account.partial.reconcile`) | Связь «оплата абонемента ↔ списания визитами ↔ сгорание остатка»: остаток предоплаты = несверенная сумма |
| Deferred revenue (Enterprise-идея, реализуем сами): предоплата на счёт обязательств, признание дохода частями | **Абонементы**: оплата → обязательство; Visit → признание дохода; истечение → признание остатка; заморозка → сдвиг срока без проводки |
| Журналы (касса, банк, продажи, разное) | Касса/банк и тип оплаты в событии |
| Аналитика (`analytic`, распределение по аналитическим счетам) | Специалист, филиал, услуга как измерения отчётов и база оплаты тренеров |
| Идемпотентность — у Odoo явной нет, но JSON-2 = транзакция на вызов | Нам: уникальный ключ `(organization_id, source_type, source_id, event_type)` + outbox, если появятся внешние получатели |
