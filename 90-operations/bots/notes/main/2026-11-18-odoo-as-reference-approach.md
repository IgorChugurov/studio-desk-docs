# Odoo Community как образец: проработка подхода для полноценной бухгалтерии SK + UA

Дата: 2026-11-18 · Автор: главный бот · Статус: рабочая заметка, **не канон и не решение**.
Предыдущая заметка: [`2026-11-18-odoo-vs-own-accounting.md`](./2026-11-18-odoo-vs-own-accounting.md) (Odoo как движок и перепись на Nest отвергнуты).

Вводные от Игоря (2026-11-18):
1. Учёт = **полноценная бухгалтерия с налоговой отчётностью для Словакии и Украины**, а не только управленческий.
2. Стратегию (отдельный OblikFlow или модуль внутри Studio Desk) надо выбрать, нужны варианты.
3. Подход: изучить открытый код Odoo Community (модель данных и все флоу бухгалтерии и других открытых модулей), взять за основу и адаптировать под наши процессы.

Пометки: **[факт]** проверено по коду или источнику; **[оценка]** моя оценка; **[мнение]** моя позиция; **[не проверено]** надо уточнить. Код Odoo смотрел в ветке `20.0`, коммит `373b237` (2026-11-18).

## 0. Выжимка

- **Подход жизнеспособен [мнение]**, если брать у Odoo **модель и правила** (сущности, связи, состояния, инварианты, флоу), а не код. У Odoo это лучший открытый образец двойной записи для малого и среднего бизнеса.
- **Что Odoo даст:** ядро двойной записи, журналы, налоги с распределением по счетам и налоговым «клеткам» отчёта, фискальные позиции, оплаты и сверку, курсовые разницы, lock dates, нумерацию, сторно, аналитику, модели касс POS, бонусов/кошельков (loyalty), формат электронных счетов UBL/Peppol BIS.
- **Чего Odoo не даст [факт]:** словацкой и украинской отчётности. В Community для SK есть план счетов, ставки DPH и структура декларации DPH (`DPHv25`), для UA — только план счетов и налоги. Нет kontrolný výkaz, eKasa, выгрузки в eDane, ПРРО, ЄРПН/податкових накладних, XML-форм ДПС, КЕП. Нет абонементов, онлайн-записи и зарплаты (только Enterprise). Это всё — наша работа.
- **Честно про объём [оценка]:** полноценная бухгалтерия двух юрисдикций — это два отдельных продукта по сложности соответствия законам, с ежегодными изменениями. Для одного человека с агентами реалистично только **по очереди: одна юрисдикция, одна организационно-правовая форма**, потом следующая.
- **Стратегия [мнение]:** вариант (iii) в практичной форме — бухгалтерия как **ограниченный модуль платформы** (отдельная схема БД `accounting`, свой Nest-модуль, вход только через события/порты), в том же деплое, что и Studio Desk; «OblikFlow» — продукт/пресет платформы без расписания (такой пресет `OblikFlow Accounting` уже есть в миграции бэкенда). Вынос в отдельный сервис — потом, если понадобится.
- **Первый шаг:** справочный документ №1 «Ядро проводок Odoo» по шаблону из раздела F + список вопросов боту «Налоги и бухгалтерия SK» + решение Игоря о первой юрисдикции и орг-форме.

## A. Правовые рамки подхода (факты и риски, не юридическое заключение)

### A.1 Что охраняется, а что нет
- **[факт]** Odoo Community — LGPLv3; файлы — © Odoo S.A. и контрибьюторов (`LICENSE`, `COPYRIGHT` в репо). Модули OCA — AGPL-3 (GitHub API: `OCA/account-financial-tools`, `account-financial-reporting`, `contract`). Odoo Enterprise — OEEL v1.0, код закрыт ([Licenses](https://www.odoo.com/documentation/19.0/legal/licenses.html)).
- **[факт]** В ЕС авторское право на программы не охраняет «идеи и принципы, лежащие в основе любого элемента программы, включая интерфейсы» — Директива 2009/24/EC, ст. 1(2) ([EUR-Lex](https://eur-lex.europa.eu/eli/dir/2009/24/oj)). Суд ЕС в деле SAS Institute v World Programming (C-406/10) указал, что функциональность, язык программирования и формат файлов данных не являются формой выражения программы ([curia](https://curia.europa.eu/juris/liste.jsf?num=C-406/10)).
- **Вывод (риск-оценка, не заключение):**
  - Низкий риск: брать **концепции** (проводка = шапка + строки, баланс строк = 0, lock dates, сторно новой проводкой, распределение налога по счетам), **названия полей как факты**, **конечные автоматы состояний**, **сценарии** (что должно происходить при оплате, частичной оплате, возврате).
  - Средний риск: близко повторять **структуру конкретных классов/методов** и их разбиение 1:1, переводя код построчно с Python на TypeScript. Это может считаться производным произведением, и тогда порт попадает под LGPL.
  - Высокий риск: копировать **код, тесты, SQL, XML-данные, тексты UI/переводов** Odoo; любое чтение кода Enterprise (нарушение договора/лицензии, у нас доступа и нет).
- **Данные локализаций:** CSV/XML в `l10n_sk`, `l10n_ua` — часть LGPL-пакета (у `l10n_sk` автор 26HOUSE, у `l10n_ua` — ERP Ukraine, [факт] по `__manifest__.py`). Но **сами планы счетов и ставки — нормативные акты**: SK — рамкова účtová osnova (opatrenie MF SR č. 23054/2002-92) **[не проверено: актуальная редакция]**, UA — План рахунків, наказ Мінфіну № 291 від 30.11.1999 **[не проверено: актуальна редакція]**. Тексты законов и официальных актов обычно не охраняются авторским правом (SK: zákon 185/2015 Z. z., § 5; UA: закон № 2811-IX) **[не проверено: точные статьи]**. Правило: **данные брать из официального источника, не из CSV Odoo**; Odoo использовать только для сверки «ничего ли не забыли».
- **OCA (AGPL):** читать для идей можно по тем же правилам. Если бы мы взяли и изменили OCA-код в сетевом сервисе, AGPL потребовал бы раскрыть исходники. Поэтому код OCA не берём.
- **Товарный знак «Odoo»:** не использовать в названиях, UI и маркетинге; в нашей документации допустимо упоминать как источник идей **[мнение]**.

### A.2 Практические правила для агентов Cursor («похоже на clean-room»)
Полноценный clean-room требует разных людей для анализа и реализации. У нас один человек и агенты, поэтому это **процесс, снижающий риск, а не гарантия** [мнение].

1. **Три фазы, три разных контекста.**
   - *Анализ:* агент-исследователь читает код Odoo Community/OCA и пишет справочный документ **своими словами**: сущности, поля (имена как факты), связи, состояния, инварианты, флоу, сценарии. Фиксирует коммит Odoo и пути файлов.
   - *Спецификация:* Игорь превращает выводы в канон Studio Desk/OblikFlow **в наших терминах** (не «account.move», а наша сущность), с AC-1..N.
   - *Реализация:* агент-исполнитель работает **только по канону**; репозиторий Odoo в его рабочем пространстве отсутствует, в правилах репо прямо запрещено открывать `odoo/*`.
2. **В справочных документах нельзя:** куски кода, SQL, регулярные выражения, тексты ошибок, XML/CSV-данные, тексты тестов Odoo. Можно: имена моделей/полей/методов в обратных кавычках, ссылки на файл и строку, пересказ логики, свои схемы и таблицы.
3. **Тесты** пишем из канона (свои сценарии). Сценарии Odoo-тестов можно пересказывать словами как чек-лист «что проверить».
4. **Enterprise-код не открывать никогда**; документацию Enterprise на odoo.com (пользовательская, публичная) читать можно — это описание функций, а не код.
5. **Данные законов** — только из официальных источников (Slov-Lex, financnasprava.sk, zakon.rada.gov.ua, tax.gov.ua), с датой редакции.
6. **Происхождение:** у каждого справочного документа шапка «Источник: odoo/odoo@<commit>, файлы …; Автор: …; Дата». У каждого канонического документа — ссылка на справочный, но без кода.
7. **Ревью на «похожесть»:** перед мержем крупного куска агент-ревьюер сравнивает структуру нашего модуля с Odoo и отмечает места, где совпадение не объясняется предметной областью.

### C.3 Флоу и как они ложатся на наши процессы

1. **Счёт клиенту → проводка → оплата → сверка** [факт по коду]. Черновик `account.move` (`out_invoice`) → `action_post`/`_post` присваивает номер, проверяет баланс и lock dates → строки: доход (product), налог (tax), дебиторка (payment_term). Оплата `account.payment` создаёт проводку «банк/касса ↔ дебиторка», затем `reconcile` связывает строки дебиторки через `account.partial.reconcile`; `payment_state` счёта становится `partial/paid`.
   - **direct_check** (разовая оплата визита): событие `visit.completed` + `payment.received` → проводка «касса/банк Дт — доход Кт — НДС Кт» в одном документе (аналог `out_receipt`). Для SK/UA при оплате на месте — фискальный чек (eKasa/ПРРО) — отдельный внешний шаг.
   - **external_order** (заказ-наряд, B2B): ближе всего к `out_invoice` с отсрочкой платежа и последующей сверкой. С 2027 в SK для B2B между плательщиками DPH — e-faktúra (Peppol BIS).
2. **Абонемент как предоплата** (в Community образца нет; идея из Enterprise deferred revenue, реализуем сами):
   - продажа: «касса/банк Дт — обязательство по предоплате (аванс полученный) Кт» (+ НДС с аванса по правилам юрисдикции — **вопрос налоговику**);
   - визит: «обязательство Дт — доход Кт» на стоимость визита (правило распределения цены абонемента на визиты);
   - сгорание остатка: «обязательство Дт — доход Кт» на остаток;
   - заморозка: без проводки, только сдвиг срока;
   - остаток абонемента = несопоставленная сумма обязательства по клиенту (через механизм, аналогичный `partial.reconcile`) **или** отдельный журнал баланса как `loyalty.history` (`issued / used / expiration_date`). [мнение] Второй вариант проще для UI, первый — для бухгалтерии; нужны оба: баланс визитов в журнале абонемента, деньги — в проводках.
3. **Кредит-нота / сторно** [факт]: `_reverse_moves` создаёт зеркальную проводку со ссылкой `reversed_entry_id`; для счетов — `out_refund`. Наш принцип «±1 в `accounting_events`» = сторно-событие, порождающее зеркальную проводку. **Важно:** Odoo позволяет вернуть проведённую проводку в черновик (`button_draft`, `account_move.py:6980`), если нет блокировок/хеша. **Нам это не подходит** — у нас проведённое не правится, только сторнируется.
4. **Налог в строке** [факт]: налог считается из `tax_ids` строки, раскладывается по `repartition_line` на счета и теги отчёта; бывает «по отгрузке» и «по оплате» (`tax_exigibility`, кассовый метод через `_create_tax_cash_basis_moves`). Это ровно то, что нужно для DPH/ПДВ: теги = строки декларации и kontrolného výkazu/ЄРПН.
5. **Курсовая разница** [факт]: проводка в валюте документа (`amount_currency`) + в валюте компании (`balance`); при сверке оплаты в другом курсе создаётся отдельная проводка курсовой разницы. Нам: EUR-организация с оплатой в UAH/USD и наоборот.
6. **Закрытие периода** [факт]: lock dates + исключения; финальное закрытие года (перенос результата) в Community не автоматизировано **[не проверено полностью]**; у OCA — `account_fiscal_year_closing`. Нам: период `open → closing → closed`, закрытие года = проводка переноса результата.
7. **Оплата исполнителям** (образца в Community нет): событие «начисление специалисту» (процент/ставка/гарантия) → «расход Дт — расчёты с исполнителем Кт»; выплата → «расчёты Дт — касса/банк Кт». Если исполнитель — сотрудник, это зарплата (отдельная тяжёлая тема: налоги и взносы SK/UA); если ФОП/SZČO — счёт поставщика (`in_invoice`).

### C.4 Связь с принципом `accounting_events`
[мнение] Слоистая схема:
- **Операционные модули** пишут доменные события (`visit.completed`, `subscription.sold`, `subscription.expired`, `payment.received`, `specialist.accrued`) — бизнес-язык, без счетов.
- **Правила проводок** (posting rules) пакета юрисдикции превращают событие в черновик проводки (счета, налоги, аналитика). Это аналог того, что Odoo делает внутри `_post` и связанных методов, но у нас явно и тестируемо.
- **Проведение** (`posted`) — неизменяемо; ошибки — сторно.
- Внутри одной БД событие и проводка пишутся **в одной транзакции** (атомарность визита и денег); уникальный ключ источника защищает от двойной записи.

### C.5 Что у Odoo сделано плохо или нам не подходит [мнение на основе фактов]
- **Мультитенантность:** изоляция компаний — record rules в одной БД либо база на клиента (см. предыдущую заметку). У нас — `organization_id` + двойной фильтр + отдельные DB-пользователи; этот уровень сохраняем.
- **Связность с ORM:** логика размазана по вычисляемым полям (`compute`), `onchange`, синхронизации «динамических строк» (`_sync_dynamic_lines`, `needed_terms`) — строки налога и дебиторки пересчитываются из строк товара при каждом изменении черновика. Это мощно для UI, но тяжело для понимания и тестирования. Нам: явный расчёт черновика чистой функцией «документ → строки».
- **Сброс в черновик проведённого** (`button_draft`) — противоречит нашему принципу неизменяемости.
- **Документ = проводка:** у Odoo счёт и проводка — одна запись `account.move`. Нам удобнее разделить «первичный документ» (счёт, чек, акт; со своими фискальными статусами eKasa/ЕРПН/e-faktúra) и «проводку» (бухгалтерия) — так их жизненные циклы не мешают друг другу [мнение].
- **Float в Python:** суммы `Monetary` хранятся в Postgres `numeric`, но считаются в Python как float с округлением по валюте. Нам: целые minor units или decimal-библиотека [мнение].
- **Отчёты** — движок `account.report` (определения в Community, рендер в Enterprise `account_reports`). Нам — свои отчёты по проводкам и тегам.

### D.3 Объём и риски [оценка, честно]
- **Общее ядро** (проводки, журналы, налоги-теги, периоды, сторно, нумерация, оплаты/сверка, валюты) — по образцу Odoo: ~2–4 месяца до надёжного состояния с тестами, для одного разработчика с агентами.
- **Пакет одной юрисдикции и одной формы** (например, SK s.r.o. плательщик DPH: план счетов, налоги, priznanie DPH, kontrolný výkaz, e-faktúra через poštára, eKasa через провайдера, годовая závierka и DPPO-данные) — ещё ~6–12 месяцев, затем постоянное сопровождение изменений закона (в SK крупные изменения в 2025, 2026, 2027, 2030 — см. выше).
- **Вторая юрисдикция** (UA: ФОП 3 гр. + ПРРО + ТОВ с ПДВ/ЄРПН/КЕП) — сопоставимый объём.
- **Риски:** юридическая ответственность за неверную отчётность; постоянные изменения законов; необходимость реальных бухгалтеров-тестировщиков; объём поддержки клиентов. [мнение] Без партнёра-бухгалтера в каждой стране обещать «полноценную бухгалтерию» опасно.
- **Порядок [мнение]:** (1) общее ядро; (2) **SK s.r.o.** (двойная запись — это и есть ядро Odoo, максимум переиспользования) + eKasa для студий; (3) SK SZČO как упрощённые режимы поверх тех же событий; (4) UA ФОП 3 гр. + ПРРО; (5) UA ТОВ с ПДВ. Выбор первой пары — за Игорем.

- вынос в отдельный сервис — только при реальной причине (нагрузка, отдельная команда, продажа как API).

### F.6 Риски подхода и как их снизить
| Риск | Снижение |
|---|---|
| Тянем сложность ERP в продукт для малого бизнеса | Брать из Odoo только модель данных; UI — два уровня: «владелец» (деньги, абонементы, выплаты, налоги к оплате) и «бухгалтер» (проводки, отчёты). Каждую сущность обосновывать нашим сценарием. |
| Объём (две юрисдикции) | Одна юрисдикция и одна орг-форма за раз; ядро общее; фискальные интеграции через провайдеров (eKasa, ПРРО, Digitálny poštár). |
| Юридический риск порта | Правила A.2, разделение контекстов, ревью на похожесть, данные только из законов. |
| Ошибки в налогах | Живой бухгалтер-тестировщик; эталонные сценарии от налоговика; тесты на каждую строку декларации. |
| Изменения законов | Пакет юрисдикции с версиями правил по датам действия (налог «действует с … по …»); календарь изменений (2027 e-faktúra, 2030 отмена KV). |
| Застревание в изучении | Ограничить итерацию изучения по времени; справочный документ — не больше одной темы. |
