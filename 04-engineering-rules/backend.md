# Правила бэкенда

**Scope:** как ведётся разработка в репозитории `studio-desk-backend`: стек, конфигурация и секреты, миграции, тесты, локальные команды.

## Эссе — что это

Правила описывают, чем и как пишется бэкенд, чтобы любой участник или агент работал одинаково. Устройство приложения описано в `03-architecture/backend-structure.md`, общие правила API — в `03-architecture/api-conventions.md`. Здесь они не повторяются.

## Эссе — стек

| Что | Чем |
|---|---|
| Среда выполнения | Node.js 24 LTS. Версия фиксируется в `.nvmrc` и одна и та же локально, в GitHub Actions и в `Dockerfile` |
| Менеджер пакетов | pnpm |
| Фреймворк | Nest, последняя стабильная версия на момент создания проекта |
| База и миграции | PostgreSQL, Drizzle |
| Проверка данных и настроек | Zod |
| Тесты | Vitest |

## Эссе — конфигурация и секреты

Репозитории открытые, поэтому секреты живут только в `.env` на машине разработчика и на сервере.

- `.env` в `.gitignore` и в репозиторий не попадает никогда.
- `.env.example` лежит в репозитории: тот же список настроек с заглушками вместо паролей и пояснением к каждой строке.
- При старте приложение проверяет все настройки схемой Zod. Если настройки нет или она неверного формата, приложение не стартует и называет эту настройку.
- Базовые настройки: адрес базы (хост, порт, имя), пароли четырёх пользователей PostgreSQL, порт приложения, режим (разработка, тесты, сервер). Настройки конкретных фич добавляются в задачах этих фич.
- На сервере `.env` создаётся вручную, один раз, прямо на сервере.

## Эссе — миграции

Схема базы меняется только миграциями Drizzle, которые выполняются под `studio_desk_owner`. Выдача прав пользователям API записывается своим SQL в миграции, в том же цикле, что и создание таблицы, с обновлением файла ожидаемых прав (см. `03-architecture/backend-structure.md`).

## Эссе — тесты

- **Модульные** — чистая логика без базы и HTTP.
- **Интеграционные** — настоящий HTTP-запрос к приложению и настоящая база PostgreSQL. Моков базы нет: часть защиты живёт в самой базе, и мок её не проверит.
- **Тестовая база** `studio_desk_test` в том же Docker-контейнере, создаётся стартовым скриптом. Перед запуском тестов к ней применяются все миграции, перед каждым тестом данные очищаются. Рабочая база тестами не затрагивается.
- **Обязательные тесты механизма:**
  1. права в базе совпадают с файлом ожидаемых прав;
  2. каждый адрес каждого из трёх API без токена отвечает отказом, кроме явно помеченных открытых;
  3. код каждого API работает только через своё подключение, и база отклоняет действия, на которые у его пользователя нет прав;
  4. неверные данные, неизвестный адрес и внутренняя ошибка возвращают ошибку в общем формате без внутренних подробностей.
- Тесты фич пишутся в задачах этих фич.
- **GitHub Actions** запускает все тесты при пуше и pull request: чистая машина, PostgreSQL той же версии, стартовый скрипт, миграции, тесты. Тестовые пароли записаны прямо в файле workflow, настоящие пароли туда не попадают.

## Эссе — локальные команды

В репозитории есть команды: поднять базу, удалить базу и создать заново, применить миграции, запустить тесты. Точные имена команд описаны в `README.md` репозитория бэкенда.

## Агент — правила

- Версии Node.js в `.nvmrc`, GitHub Actions и `Dockerfile` совпадают.
- Новая настройка: в схеме Zod и в `.env.example`, в том же изменении.
- Схема базы меняется только миграцией; права выдаются в той же миграции.
- Интеграционные тесты работают с настоящей базой, без моков базы.
- Тесты не используют рабочую базу.
